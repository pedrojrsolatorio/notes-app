# Review, main, 2026-11-09

**Reviewed by**: Crouton Alpha (author on unknown)
**Scope**: 19 files, uncommitted
**Verdict**: Blocked

## Summary

The change adds a complete offline-sync stack (sync change log, observers, GET/POST /sync, Dexie PWA, service worker). Core design is sound — tenant scoping, idempotent replay, tombstones, and per-user stores all follow the spec. However, the sync write path never emits change-log rows for updates, trash/restore, or folder renames, so a second device never receives those edits. Offline trash-after-edit is also coalesced away, and the service worker can serve the previous user's shell, both of which break data integrity and user isolation.

## Blockers

### 🔴 Missing change-log rows for sync write-path mutations, `app/Http/Controllers/SyncController.php:345`
**Problem**: `updateNote()` (normal and folder-move paths), `trashNote()`, `restoreNote()`, and `renameFolder()` return `applied` without calling `SyncChange::record()`. They run inside `ChangeRecorder::withoutRecording()`, so observers are suppressed and no row is written. Only `created`, `purged`, conflict copies, and folder deletes write rows.
**Why it matters**: Other devices pulling via `GET /sync?since=<cursor>` never see offline-edited notes or renamed folders. The edit exists on the server but is invisible to every other device until a manual `since=0` resnapshot, violating AC-6 and making sync silently diverge. `server_revision` also stalls because it is the max `sync_changes.id`.
**Suggested fix**: Record exactly one `sync_changes` row inside the same transaction for every applied write-path mutation (note `updated`/`deleted`/`restored`, folder `updated`), carrying the `client_change_id` and `applied` status, mirroring the existing create/purge paths.

### 🔴 Outbox coalescing keeps `updated` over `deleted`/`purged`, `resources/js/offline-app.js:128`
**Problem**: `queueOutbox()` merges with `ACTION_PRIORITY` min. After an offline edit queued as `updated`, a subsequent trash (`deleted`, priority 2) or purge (priority 1) keeps `updated` and overwrites the payload with `{}`.
**Why it matters**: Trash or purge offline after an edit loses its intent. The server receives `updated` with empty payload, keeps the note alive, clears its folder, and loses the edited title/content. The note can never be trashed or permanently deleted offline if it was edited first.
**Suggested fix**: Coalesce to end-state action (keep `created` if either side was `created`, otherwise the newest action wins) while retaining the earliest `base_version` and a payload that reflects the final state.

### 🔴 Service worker cache-first serves stale per-user `/app` shell, `public/sw.js:55`
**Problem**: The `fetch` handler returns `caches.match('/app')` immediately for navigations before the network settles. The cached `/app` HTML embeds the previous user's `data-user-id` and CSRF token. `boot()` trusts `pageUserId()` from that cached DOM before probing the server.
**Why it matters**: User B signing in on a browser that cached User A's shell opens `notes-offline-<A>` and shows A's notes, violating AC-9b user isolation. The stale CSRF also forces a 419 round-trip on every sync.
**Suggested fix**: Do not cache authenticated HTML containing user identity. Use network-first for `/app` navigation (fall back to cache only offline) and make `boot()` prefer a fresh session probe over the cached `data-user-id` when online.

## Major

### 🟠 Stale folder rename and remote folder delete never win locally, `resources/js/offline-app.js:407`
**Problem**: The push `rejected` branch marks the entity `conflict` and shows a notice but never applies `result.folder`. Pull also skips a `deleted_folder_portable_ids` entry when a pending folder change exists. Server-side, the stale-rename early return in `renameFolder()` (`app/Http/Controllers/SyncController.php:532`) returns `rejected` without persisting a `sync_changes` row.
**Why it matters**: AC-8 requires the server name applied and a remote folder delete to move local notes to All Notes. Currently the local rename/delete intent persists indefinitely and the two devices diverge forever.
**Suggested fix**: Persist the stale-rename outcome server-side for idempotency, and on rejected folder results apply the authoritative server folder state (or delete the folder and null its notes) before dropping the outbox row.

### 🟠 Pull transaction reads `outbox` outside its Dexie scope, `resources/js/offline-app.js:255`
**Problem**: The pull transaction declares `[db.notes, db.folders, db.sync_meta]` but calls `hasPending()`, which queries `db.outbox`.
**Why it matters**: Dexie requires every table touched inside a transaction to be in scope. This can throw an inactive-transaction error or introduce races, stalling sync on some browsers.
**Suggested fix**: Include `db.outbox` in every transaction that calls `hasPending()`.

### 🟠 Editor panel blanks after the first full render, `resources/js/offline-app.js:1268`
**Problem**: `renderAll()` calls `root.replaceChildren()` which destroys the editor DOM. `renderEditor()` then takes the `editorNoteId === portable_id` branch and returns without recreating the editor, leaving `#editor-panel` empty.
**Why it matters**: After any save or completed sync, the Tiptap editor disappears and unsaved typing is lost. The offline view becomes unusable after the first action.
**Suggested fix**: Rebuild the editor panel whenever the DOM was recreated, or preserve the editor node across renders.

### 🟠 Malformed payload aborts the whole batch with 500, `app/Http/Controllers/SyncController.php:78`
**Problem**: Validation only checks `payload` is an array; `title`/`content` types inside it are unchecked. A `content` array reaches `create()`/`save()` and throws. The `foreach` loop has no per-change try/catch, so one bad change discards the rest of the batch.
**Why it matters**: Violates the spec's per-change rejection in a 200 response. A single forged or buggy client change becomes a 500 for the whole request and blocks unrelated queued edits.
**Suggested fix**: Validate payload shape strictly (string `title`/`content`, UUID-or-null `folder_portable_id`, etc.) and isolate each `applyOne()` so failures become `rejected` results.

### 🟠 Absent `folder_portable_id` clears the folder, `app/Http/Controllers/SyncController.php:319`
**Problem**: `resolveFolder($payload['folder_portable_id'] ?? null)` treats a missing key identically to explicit `null` (All Notes). `updateNote()` then force-fills `folder_id` to null.
**Why it matters**: Title/content-only edits that omit the folder field silently move the note to All Notes, destroying folder assignment.
**Suggested fix**: Use `array_key_exists` to distinguish absent from explicit null; only move the note when the key is present.

## Minor

### 🟡 Conflict copy title comes from the server title, `app/Http/Controllers/SyncController.php:401`
**Problem**: `conflict()` builds `Conflict copy of <server title>` while content is the queued version. The spec ties title and content to the queued change.
**Why it matters**: The copy is confusingly labeled with the opponent's title and loses the offline title.
**Suggested fix**: Derive the title from the queued payload title (falling back to server title only when absent), truncated to 255 code points.

### 🟡 Snapshot rejects `limit` even though it is ignored, `app/Http/Controllers/SyncController.php:34`
**Problem**: `limit` is validated (`between:1,1000`) before the `since === 0` snapshot branch, though the spec says snapshot ignores `limit`.
**Why it matters**: A snapshot request with an out-of-range `limit` returns 422 instead of a snapshot.
**Suggested fix**: Only validate `limit` when `since !== 0`.

### 🟡 410 cursor returns `minRetained - 1`, `app/Http/Controllers/SyncController.php:146`
**Problem**: The 410 response returns `max(0, minRetained - 1)`, but the spec requires the minimum retained revision.
**Why it matters**: Clients that honor the advertised cursor resume from the wrong point.
**Suggested fix**: Return the minimum retained revision exactly as specified.

### 🟡 Folder delete of unknown id returns `applied`, `app/Http/Controllers/SyncController.php:567`
**Problem**: `deleteFolder()` returns `applied` when the folder is not found, while note updates for unknown ids return `rejected`. Forged folder ids therefore masquerade as success.
**Why it matters**: Violates the forged-id-is-rejection contract in AC-11.
**Suggested fix**: Return `rejected` (or at least distinguish forged from already-deleted) for folder deletes that never existed for this user.

### 🟡 Trashed notes missed on folder delete via sync, `app/Http/Controllers/SyncController.php:580`
**Problem**: `deleteFolder()` collects via `Note::where('folder_id', ...)` without `withTrashed()`, but `FolderObserver` uses `withTrashed()`.
**Why it matters**: Trashed notes in a deleted folder get no version bump or change row from the sync path, so other devices learn of the folder move late.
**Suggested fix**: Include trashed notes consistently in both paths.

### 🟡 Backoff and rate-limit handling ignores server signals, `resources/js/offline-app.js:514`
**Problem**: `syncNow()` always schedules `backoffDelay(1)` (2s) regardless of attempts, and neither push nor pull honors `Retry-After` on 429.
**Why it matters**: Repeated failures retry too aggressively against a throttled endpoint.
**Suggested fix**: Derive delay from the outbox attempt count and `Retry-After` header.

### 🟡 Duplicate `/app` route, `routes/web.php:16`
**Problem**: `Route::view('/app', 'pwa.notes')` is registered twice with the same name.
**Why it matters**: Redundant, invites future merge confusion.
**Suggested fix**: Remove the duplicate line.

## Nits

- ⚪ `app/Observers/NoteAttachmentObserver.php:37`, `withoutTrashed()` lookup means attachment changes on trashed notes never emit a change row.
- ⚪ `resources/js/offline-app.js:186`, 419 refresh fetches a fresh CSRF token from HTML but never updates the DOM meta tag for later requests.
- ⚪ `vite.config.js:6`, `VITE_SKIP_FONTS` build flag is undocumented and changes the built artifact shape without spec coverage.

## Strengths

- Ownership is consistently enforced through `$user->notes()`/`$user->folders()` relations, forged folder/portable ids are rejected per-change, and the sync API is rate-limited per user.
- Idempotent replay via `(user_id, client_change_id)`, correct `has_more`/cursor semantics, purged-note tombstones, and conflict-copy `portable_id = client_change_id` handling are all faithful to the spec.
- Observer design centralizes Livewire mutations (version bump + change row), attachment manifest omits file bytes, `/sync` and downloads bypass the service worker cache, push ordering matches the spec, and the per-user IndexedDB split is clean.

## Test coverage

Pest covers the server API well (28 tests, 118 assertions): snapshot, pagination, 410, conflict copy, metadata-only moves, folder rules, forged ids, validation, attachment manifest, and rate limiting. The suite missed the missing change-log rows for sync-write updates/trash/restore/renames because it only asserts DB state and snapshot reads, never a second-device pull after a sync push. The Dexie client, outbox coalescing, 419 refresh, per-user shell, and service-worker behavior have no automated coverage, acknowledged by the spec as manual-verify-only, but that left the trash-coalescing and stale-shell bugs above unexercised.
