# Review, main, 2026-11-13

**Reviewed by**: big-pickle (author on big-pickle; no contrasting model was available, so this is a same model review)
**Scope**: 8 content files, uncommitted (147 mode only changes excluded; 2 binary icons)
**Verdict**: Blocked

## Summary

The remediation fixes the prior server side blockers and adds useful Pest coverage: change log rows now follow every applied mutation, malformed changes are rejected per change, folder assignment survives a metadata only update, and folder delete includes trashed notes. The remaining risk is in the offline client and service worker. The service worker can cache another user's server rendered notes page as the app shell, an in flight create can lose later edits or resurrect a trashed note, and offline boot can open the previous user's local store after a user switch on the website. A folder pull regression can also drop a pending folder delete when a stale rename loses. Because this review and the author share the same model, treat the findings as a second pass with the same blind spots, not as a cross model guarantee.

## Blockers

### 🔴 Service worker caches every navigation as the app shell, `public/sw.js:62`
**Problem**: The navigation branch stores every successful same origin navigation response under `/app`, not only the response for `/app`. That includes `/notes`, which is server rendered with the signed in user's notes, `/dashboard`, and login redirects. Offline, `caches.match('/app')` returns that stored page as the installed app. User A's `/notes` page can therefore be shown to user B offline, and the installed app can open a page that never loads `offline-app.js`.
**Why it matters**: This breaks AC-4 (offline shell) and AC-9b (user isolation), and it can expose another user's note content from the browser cache.
**Suggested fix**: Cache only a navigation whose `url.pathname` is `/app` and whose response is not redirected. Keep the fallback keyed to the real `/app` shell, and never store `/notes`, `/dashboard`, or auth redirects under `/app`.

### 🔴 In flight creates lose later edits and can resurrect trashed notes, `resources/js/offline-app.js:484`
**Problem**: While a create is sending, the local note still has `last_synced_at` set to null. A later save calls `saveNote()` and queues another `created` change. The server's `createNote()` sees the existing portable id and returns the old note without applying the new title or content, and the next pull overwrites the local edit. Trashing or purging while the create is sending deletes the sending outbox row and the local note, but the server create still succeeds, so the note reappears on the next pull.
**Why it matters**: This is data loss and a resurrected delete, and it violates AC-2, AC-3, and AC-10b.
**Suggested fix**: When the create response arrives, set `last_synced_at` and the server version on the local note even while it stays pending. Do not delete outbox rows with status `sending`; convert a later edit to an `updated` change or queue the delete after the create. The server's existing note branch must not silently accept a different payload as a replay.

### 🔴 Offline boot can open the previous user's store, `resources/js/offline-app.js:1539`
**Problem**: `let userId = pageUserId() ?? lastUserId()` prefers the cached shell's `data-user-id`. The online probe corrects it, but offline there is no probe. If user B signs in on the website without opening `/app` online, the cached shell and `last_user_id` still point to user A, so B sees A's local notes. A 500 from `/app` also returns `undefined` and keeps the cached user, so a server error can open the previous user's store too.
**Why it matters**: This violates AC-9b and exposes one user's local notes to another user on a shared browser.
**Suggested fix**: Update `last_user_id` during the web sign in flow, or clear the app shell cache on an auth change. Do not fall back to the cached shell user when an online probe fails; show a sign in or error state instead. When offline, use the stored last user only when it is known to match the current session.

## Major

### 🟠 Stale folder rename can drop a pending delete or a valid newer rename, `resources/js/offline-app.js:305`
**Problem**: The pull picks the first pending `updated` row, applies the server folder when the server version is newer, and then deletes every pending folder row. That includes a queued `deleted` action and a newer rename that is still valid. A user who renames a folder while it is sending and then deletes it before the rename response can have the delete dropped and the server folder reappear. The local notes were already moved to All Notes, so the folder and the notes diverge.
**Why it matters**: The folder delete intent is lost and the folder reappears, which violates AC-3 and AC-8.
**Suggested fix**: Treat a pending `deleted` action as the local end state and do not apply the server folder or delete the delete row. Compare against the newest pending rename (highest `base_version`), and drop only the stale rename rather than every pending folder row.

## Minor

### 🟡 403 and 422 responses retry forever, `resources/js/offline-app.js:200`
**Problem**: `fetchSync()` treats 401, 3xx, and 419 as needs sign in. A 403 from an unverified session and a 422 from batch validation fall through, so `push()` and `pull()` throw a generic error and retry with backoff. A permanently invalid batch or an unverified session never becomes terminal or a sign in prompt.
**Why it matters**: The outbox can be stuck indefinitely and the user only sees a generic error, which conflicts with AC-9 and AC-10c.
**Suggested fix**: Treat 403 as needs sign in or verification. For 422, surface the validation error and drop or quarantine the offending outbox rows instead of retrying the same batch forever.

### 🟡 Raw exception reporting can log note content or titles, `app/Http/Controllers/SyncController.php:242`
**Problem**: `report($exception)` logs the raw exception. A `QueryException` during note creation or update can include SQL bindings with the note title or content.
**Why it matters**: The security model says logs never include note content, titles, or portable ids.
**Suggested fix**: Log a sanitized message with the exception class and a generic sync failure, and keep the SQL bindings out of the log.

### 🟡 Duplicate client change id race can return 500, `app/Http/Controllers/SyncController.php:244`
**Problem**: If two requests with the same `client_change_id` race, the loser can hit the unique `(user_id, client_change_id)` index. The catch then tries to insert a rejection row with the same key and fails again, returning 500 instead of replaying the winner.
**Why it matters**: A retry after a timeout can fail before the client retries again, producing transient 500s and noisy logs.
**Suggested fix**: In the catch, look up an existing row with the same `client_change_id` and replay it, or handle the unique violation separately with `firstOrCreate`.

### 🟡 Offline client changes have no automated coverage, `resources/js/offline-app.js:1539`
**Problem**: The changed identity, folder pull, and navigation caching branches have no automated tests. The spec relies on manual verify, but the current verify file does not exercise a website user switch followed by an offline app open, a navigation to `/notes` before an offline launch, or an edit or trash while a create is sending.
**Why it matters**: The three blockers above would pass the current Pest suite.
**Suggested fix**: Add those scenarios to `docs/specs/0004-offline-use-and-device-sync/verify.md` now, and add a JavaScript runner later if the project approves it.

## Nits

- ⚪ `public/sw.js:6`, the cache name is static, so old hashed assets are never removed across deploys.
- ⚪ `public/sw.js:62`, the cache write promise is not awaited or caught, so a cache failure can produce an unhandled rejection.
- ⚪ `resources/js/offline-app.js:309`, the pending folder check uses the first rename rather than the newest, which is the same root cause as the folder pull major.

## Strengths

- The server side remediation is careful: one change row per applied mutation, per change malformed rejection, folder preservation on metadata only updates, and trashed notes included in folder delete.
- Ownership scoping and idempotent replay remain consistent, and the new Pest tests cover the review fixes well (34 tests, 165 assertions).
- The service worker fallback now returns a real 503 instead of `undefined`, and the offline app distinguishes a confirmed sign out from a failed probe.
- The restored import export view and the duplicate Vite config removal are clean and narrowly scoped.

## Test coverage

Pest covers the server changes well: the new tests exercise trashed notes on folder delete, an unexpected exception inside the transaction, malformed batches, folder preservation, and change rows for applied mutations. The changed Dexie client and service worker logic has no automated coverage, and the manual verify file does not cover the user switch offline, the navigation cache poisoning, or the in flight create race. Those gaps match the blockers above.
